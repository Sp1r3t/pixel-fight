# Архитектура Pixel Fight

Короткий справочник по ключевым решениям. Детали реализации появляются по этапам (см. README).

## 1. Сервер — единственный источник правды

- Бой симулируется **только на сервере** с фиксированным шагом **60 Гц** (`GameConfig.TickRate`).
  Вся фреймдата (startup / active / recovery, hitstun, blockstun) задана в кадрах этой симуляции.
- Клиент отправляет **только ввод**: битовую маску кнопок (влево, вправо, вверх, вниз, рука, нога,
  особый, супер) и номер своего кадра. Никаких позиций, урона или «я попал».
- Урон, хитбоксы, здоровье, шкала супера, таймер раунда, победы — считаются только на сервере
  (`CombatService`, `MatchService`).
- Антиэксплойт (`InputService` + `CombatService`):
  - лимит частоты пакетов ввода на игрока, отбрасывание устаревших/повторных пакетов;
  - приём можно начать только в допустимом состоянии бойца (кулдауны и фреймдата проверяются сервером);
  - дистанция и хитбоксы проверяются сервером, клиентские «попадания» не существуют;
  - ввод принимается только от участника матча и только для его бойца.
- Компенсация пинга: при проверке попадания сервер допускает небольшое окно задержки — хартбокс цели
  сравнивается с её положением за последние N мс (N ограничен сверху, чтобы игрок с огромным пингом
  не получал преимущества).
- ИИ боссов выдаёт **ввод**, который проходит через тот же конвейер, что и ввод игроков.

## 2. Отрисовка: 2D в 3D-мире

- Арена — плоскость в Workspace, бойцы двигаются только по X (и прыгают по Y).
- Спрайты — `ImageLabel` в `SurfaceGui` на невидимой детали: `ImageRectOffset`/`ImageRectSize`,
  `ResampleMode = Pixelated`. Зеркалирование — отрицательный `ImageRectSize.X`
  (запасной вариант — зеркальные кадры прямо в спрайт-листе).
- Камера — `Scriptable`, сбоку, с узким FOV (почти ортографическая проекция).
- Почему не чистый ScreenGui: в мире работают `ParticleEmitter`, освещение/`Bloom` для вспышек суперов,
  тряска камеры через `CFrame`, параллакс фона — всё это нужно для «сочного» боя.
- Стандартный персонаж Roblox не используется (`Players.CharacterAutoLoads = false`), меню — на Fusion.
- Пока нет нарисованного арта, бойца рисует `Sprites/Rig`: скелет из скруглённых `Frame` с обводкой,
  каждый между двумя суставами (позиция — середина отрезка, `Rotation = deg(atan2(-dx, dy))`).
  - Всё считается в пространстве «смотрит вправо» в долях клетки спрайта; поворот — зеркально `x → 1 − x`,
    угол → −угол.
  - Позы (`RigPoses`) — ключевые кадры углов суставов. Удары берут прогресс из фреймдаты, поэтому
    картинка совпадает с хитбоксами сервера.
  - Облик — данные (`Config/CharacterLooks`), цвета — слоты палитры, так что боссы перекрашиваются
    без отдельного арта.
  - Ткань — verlet-цепочки с ограничением шага. Интерфейс аниматора общий с `SheetSprite`: настоящие
    спрайт-листы подключаются полем `sprites` без правок кода.
- Портреты в меню (`UI/Components/FighterPortrait`) — тот же Rig в рамке с `ClipsDescendants`. Статичные
  портреты не обновляются; анимированные обновляет одна общая подписка ~30 кадров/с.

## 4. Баланс без pay-to-win

1. У каждого персонажа 5 рейтингов (HP, урон, скорость, дальность, набор супера) от 2 до 8,
   **сумма ровно 25**. Больше урона ⇒ меньше чего-то другого.
2. Урон особых приёмов и суперов ограничен диапазонами **по типу приёма** (`Balance.SpecialDamageBands`,
   `Balance.SuperDamageBands`): надёжные и безопасные типы (снаряд, луч на весь экран) бьют слабее,
   рискованные (контратака, захват вплотную) — сильнее. Платный персонаж получает те же диапазоны.
3. Средние рейтинги платных не могут превышать средние бесплатных больше чем на 0.75 по любой характеристике.
4. Платные персонажи (`cosmetics.tier = "Deluxe"`) получают ауры, шлейфы и особые фоны суперов —
   боевой код косметику не читает.

Сервер вызывает `CharacterRegistry.assertValid()` при старте: конфиг, нарушающий правила, не запустится.

## 4б. Особые приёмы, снаряды, суперы

- Всё поведение приёмов — в общей симуляции (`Combat/Specials`, `Combat/Projectiles`), значит, оно
  серверное, детерминированное и тестируется в Lune. Данные (фреймдата, урон, параметры) — в конфиге
  персонажей; код различает только **тип** приёма.
- Приёмы с движением (рывки, прыжки, телепорт) сами задают скорость бойца на каждом кадре
  (`Specials.update`); прыжок-дуга задаётся точной параболой, пике — прямой до пола.
- Снаряды — отдельные сущности симуляции: полёт, взаимное уничтожение, попадания проходят через
  тот же `applyHit` (блок, урон по блоку, комбо), но владелец при попадании не «застывает» и не получает отмен.
  В снапшоте — id, вид, позиция; клиент интерполирует их по id.
- Контратака проверяется до блока: удар вплотную по стойке гасится, и защитник отвечает приёмом
  (супер-контратака запускает ролик). Захваты и снаряды стойку не активируют.
- Ролики суперов режиссирует клиент (`Fight/Cinematics`): сервер держит бойцов на месте и наносит урон
  сериями, клиент лишь смещает картинку, ставит фон, камеру и эффекты — на исход боя это не влияет.

## 4а. ИИ боссов: сложность в поведении

- ИИ не трогает симуляцию: `BossAI.think(sim, slot)` возвращает только ввод (`held`/`pressed`), который
  проходит через тот же `Simulation.step`, что и ввод игроков. Тест проверяет, что `think` ничего не меняет в бою.
- Восприятие с задержкой: противника ИИ видит `reactionFrames` кадров назад (кольцевой буфер наблюдений) и
  экстраполирует движение; свои состояние и блокстан «чувствует» сразу (как человек — удар по блоку).
- Конечный автомат (`StateMachine`): Neutral (дистанция, тычки, прыжки, рывки, особые приёмы),
  Defend (блок стоя/сидя), Punish (наказание промаха), Attack (план комбо с отменами и проверкой попадания),
  AntiAir, JumpIn, Recover (оглушение, защита при вставании, контр-супер).
- Чтение привычек: частота прыжков, доля низких ударов, частота атак вблизи — ИИ старших тиров заранее
  готовит анти-эйр, угадывает стойку блока и «пережидает» натиск.
- Все параметры сложности — в профиле (`Types.AiProfile`): реакция, частота блока, чтение стойки, наказания,
  анти-эйр, качество комбо, супер, чтение, ошибки. Уровень мастерства растёт с номером босса (тест проверяет
  монотонность), стиль (`Rushdown`, `Zoner`, `Turtle`…) меняет только манеру боя.
- Случайность — детерминированный `Rng` с зерном: бои воспроизводимы, тесты стабильны.
- Механики боссов работают через `Fighter.modifiers` (множители урона, вампиризм, набор супера) и хук шага
  `BossRules.step` — общая симуляция не знает про боссов.
- Бонус HP боссов ограничен `Balance.BossMaxHpMultiplier` (1.3) — валидатор не даст его превысить.

## 5. Режим 2 на 2 — четверо на сцене с двумя этажами (как в Brawlhalla)

Сначала (этап 7) 2 на 2 был «эстафетой»: на экране всегда 1 на 1, выбывшего сменял напарник.
По просьбе заказчика на этапе 11 режим переделан: все четверо бьются одновременно на сцене
с двумя этажами — внизу пол, на средней высоте слева и справа второй этаж, в центре дыра.
Слева внизу и наверху — одна команда, справа — другая; нижние дерутся с нижними, верхние — с верхними.

Как решены проблемы совместного боя, из-за которых раньше выбиралась эстафета:

1. **Блок с двух сторон.** Появилась кнопка блока (`InputBits.Block`, Q / LT / кнопка «Блок»):
   она защищает в любую сторону. Блок «назад» по-прежнему работает — от текущей цели.
2. **Кого бить на телефоне.** Цель выбирается автоматически (`updateTargets`): ближайший не выбитый
   противник; противник на другом этаже считается дальше (×4 по высоте), текущая цель чуть
   в приоритете, чтобы не «прыгать». Этаж считается по последней опоре (`Fighter.standY`), поэтому
   прыжок над дырой цель не меняет. Удары попадают по всем противникам в хитбоксе (захват — по одному).
3. **Читаемость.** Бойцы на разных этажах не перекрываются; камера отъезжает до всей сцены
   (`Stage.cameraMaxWidth`); над бойцами — таблички цветом команды; HUD — по две строки на команду.
4. **Суперы с роликами** замораживают всю сцену, как и в 1 на 1; в ролике участвуют двое
   (событие `CinematicStart` несёт слот цели — `d`).
5. **Свои.** Урона по своим нет, союзники проходят сквозь друг друга (у сцены `pushboxes = false`).
6. **Падения.** Удар с разбега у края останавливается (падают только от удара противника или сойдя с края);
   оглушение, кончившееся в воздухе, переходит в падение с доступным двойным прыжком.

Геометрия и правила сцены — данные (`Shared/Combat/Stage.luau`): платформы, точки появления по слотам,
толкание, двойной прыжок, управление в воздухе, параметры камеры. Сцена `Duel` повторяет прежний 1 на 1,
поэтому весь 1 на 1 (и все его тесты) не изменился.

`MatchFlow` работает по командам: раунд выигрывает команда, выбившая всех соперников; по времени —
больший общий % HP команды. ИИ (`BossAI`) умеет переходить между этажами (состояние `Travel`),
перепрыгивать дыру к цели на другой половине этажа, не прыгать-атаковать в дыру и «спасаться»
двойным прыжком, если сбили. Проверка — `lune run tests/tools/team-duel.luau`.

## 5а. Матчмейкинг

1. **Внутри сервера** — очередь в памяти: как только набралось 2 (или 4) игрока, матч стартует сразу.
2. **Между серверами** (`Matchmaking/CrossServer`) — `MemoryStoreSortedMap` на режим: ключ — UserId,
   `sortKey` — время входа (первым пришёл — первым подобран), запись живёт 60 с и продлевается, пока игрок ждёт.
   Сервер берёт самые старые записи и захватывает каждую атомарным `UpdateAsync`; если хотя бы одну уже
   захватил другой сервер — отпускает свои и пробует позже. Поэтому игрок не попадёт в два матча.
3. Для собранного матча `TeleportService:ReserveServer`; каждому игроку пишется «билет» (код доступа и состав),
   сервер игрока читает билет и телепортирует его с данными матча (`TeleportOptions`).
4. **Сервер матча** распознаётся по `game.PrivateServerId ~= ""` и `PrivateServerOwnerId == 0`; принимает
   только игроков из состава, ждёт всех 30 с, проводит матч и возвращает всех в лобби.
5. **Комнаты** — код из 6 символов без похожих букв; `MemoryStoreHashMap` «код → JobId хозяина», чтобы друг
   с другого сервера телепортировался к хозяину (`TeleportOptions.ServerInstanceId`).
6. Данные телепорта (`Protocol`) проверяются так же строго, как сетевые запросы; персонажи — на владение.
7. Вся логика MemoryStore получает сервисы через параметры и тестируется на поддельном хранилище
   с несколькими «серверами» (`tests/lib/FakeMemoryStore.luau`), включая гонку захвата и отказы хранилища.

## 5б. Подготовка к бою и карты

- `DraftService` — отдельный сервис между подбором и матчем: фазы «боец» → «карта» → «показ».
  Матчмейкинг отдаёт ему слоты (люди и боты) и колбэк `onDone`, который создаёт матч по итогам;
  так очередь, комнаты, бой с компьютером и сервер матча используют одну и ту же подготовку.
- Сервер проверяет каждый выбор: бойца — по владению, карту — по владению (премиальная — только владельцу),
  фазу — по таймеру. Клиент получает полное состояние после каждого изменения (простая синхронизация).
- Карты — данные (`Config/Arenas`), отрисовка — процедурная (`Client/Fight/ArenaArt`): прямоугольники по
  сетке пикселей арта, три плоскости с параллаксом. Линия горизонта рисунка совпадает с дальним краем пола
  для обеих камер (1 на 1 и 2 на 2), детали неба — в видимой камере полосе. Анимации — функции `update(dt)`,
  которые вызывает `FightController` каждый кадр. Та же отрисовка даёт картинки карт для выбора и магазина.

## 6. Сохранения и покупки

- `DataService` открывает профиль через интерфейс `Data/Session`. В игре его реализует
  `ProfileStoreBackend` (ProfileStore).
  - Профиль открыт только на одном сервере — это защита от дюпа и потери данных.
  - Автосохранение, сохранение при выходе и `BindToClose`.
  - Профиль не открылся — игрок отключается с сообщением.
  - Профиль забрал другой сервер — игрок тоже отключается, иначе его изменения здесь потерялись бы.
- В тестах тот же интерфейс реализует `MemoryBackend`: блокировка, копии при сохранении,
  отказ сохранения, внешнее закрытие сессии.
  - Это нужно, потому что ProfileStore требует DataStore и `task.wait`, которых в Lune нет.
  - Harness подменяет модуль, как `Transport`.
- `ProfileSchema.migrate` приводит данные к текущей версии: проверяет типы и диапазоны, отбрасывает
  неизвестные поля, добавляет недостающие.
- `MonetizationService.processReceipt` защищён от двойной выдачи:
  1. если `PurchaseId` в профиле ещё нет — выдать награду и записать `PurchaseId` в профиль;
  2. дождаться, пока сохранённый снимок профиля (`LastSavedData`) содержит `PurchaseId`;
  3. только тогда вернуть `PurchaseGranted`, иначе `NotProcessedYet` (Roblox повторит чек);
  4. повторный чек с тем же `PurchaseId` лишь подтверждает сохранение, награду не выдаёт.
- Game Pass: владение проверяется при загрузке профиля (покупки на сайте) и по серверному событию
  `PromptGamePassPurchaseFinished`. Открытый боец записывается в профиль.

## 7. UI на Fusion 0.3

- Всё состояние интерфейса — Fusion `Value` в `AppState`; экраны строятся через `scope:Computed`
  и перестраиваются автоматически.
- Роутер в `App.luau`: смена `state.screen` уничтожает старый экран вместе с его scope.
- Макеты сверстаны под 960×540 и масштабируются `UIScale` под любой экран.
